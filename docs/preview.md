# 预览与检查

条目达到数千篇后，完整构建需要数十秒到数分钟。本文说明检查、`serve` 增量更新、常驻预览服务与在线编辑的设计。

## 命令

```sh
npm run check -- content/wiki/条目甲
```

`check` 只运行预处理，不生成页面：收集全部错误（而不是第一个）和缺失条目链接，按页面列出；不指定页面时检查全站，`--json` 输出 JSON。

`npm run serve` 的预览输出在 `.build/preview/`，使用开发样式和 source map。同一份源码同时只能运行一个 `serve`，第二个会提示后退出：两者会构建到同一目录。

## 依赖关系

一个页面的输出依赖：

- 本页的正文与 front matter；
- 全站 front matter：条目名与别名决定链接颜色和地址，分类、书册目录、列表页使用标题与排序键；
- 共享定义：模板、样式、`data/`、`i18n/`、学科导航的定义、构建脚本、站点设置（`site.yaml`）；
- 同一书册的其他页面：编号与跨页引用；
- Git 提交日期。

其他页面不读取百科条目的正文（跨页引用只存在于书册内），所以**只改正文时，只有本页需要重新渲染**；书册页面的正文影响同组页面的编号与引用，只需重新渲染整组书册。这是单页路径的基础。

## serve 的增量更新

`serve` 记录 `content/` 的文件列表、各页面的 front matter 与 `data/` 的文件列表（完整构建前，以及每次更新成功后）。之后的修改按下列规则处理；常驻预览服务把结果写入 `.build/preview/`，`serve` 只读回写入与删除的文件，合并进内存快照：

- 只有已有页面的正文变化（front matter 不变）：交给常驻预览服务单页更新（`render`）。书册页面（包括 `content/help/` 中的指南）重新渲染所在书册的全部页面，含自动目录页。
- 已有页面的 front matter 变化，或在已有目录中新建页面：只重新转换这些页面（`renderPages`），再重新渲染依赖它们的页面（见下文“部分重建”）。页面用到分类表中没有的分类时改用下一条（只有完整预处理才生成分类页）。
- 删除、改名、新建目录、附件、`book.yaml`、学科导航的定义、`data/categories.yaml`、Git 提交：在预览服务中完整预处理（`refreshSite`；正文多半取自渲染缓存，见下文），把变化的生成文件写入生成目录，同样重新渲染它们与依赖它们的页面。
- 样式与脚本（`assets/`）：只重新构建它们（`assets`，约 0.4 s），打开的页面都刷新；资源的地址变了（production 的指纹）才重新生成页面。
- `static/` 中的文件：只复制变化的（`staticFiles`，约 0.2 s），打开的页面都刷新。
- 站点生成器的代码（`scripts/site/`，模板、生成与完成页面）：重启生成器的线程，重新生成全部页面，不预处理（`restartGenerator` 与 `buildSite`）。生成的 HTML 与上次相同的页面不再完成、也不再写入，所以只改一种页面的模板约 2 s，改所有页面共用的部分（页眉、页脚）约 8–9 s：约 2700 个页面都要重新完成，这台 10 核的机器上再多线程也不更快。
- 其他代码（`scripts/` 的其余部分、`packages/`）、`i18n/`、其他 `data/` 文件与 `site.yaml`：重启预览服务，完整预处理，再生成全部页面（与上一条相同，未变的页面不再完成）。`i18n/` 的修改约 9 s。
- 出现又消失的路径（编辑器临时文件，包括 `data/` 中的）：忽略。
- 上次完整构建失败后，一律完整构建，直到成功。源文件的错误（预处理失败）不改变任何状态，修正后连同这次的修改一起处理；部分重建的其他失败（如模板出错）改为完整构建。

完整构建的预处理也在预览服务中完成，所以服务始终持有最近一次成功的全站状态。服务在完整构建成功后于后台预热（见下文）。单页结果与完整构建逐字节一致，`tests/serve.mjs` 检查了这一点；在真实内容上，经过多次启动与修改之后的 `.build/preview/` 也与同一地址的完整构建逐字节相同（搜索索引除外）。

站点生成器（`scripts/generator.mjs`）在预览服务中以 worker 线程运行：两个线程各持有全站的页面，分担运行模板（`scripts/site/core.mjs`：渲染页面、站点地图等全站文件、搜索清单、样式与脚本、复制 static/），其余的核完成页面（排版与搜索文档，没有 TikZ 图形的页面由完成它的线程直接写出）；TikZ 与搜索索引在服务的主线程。页面模板把正文标出（`data-typeset-body`），完成页面时排版跳过它（bananamark 已经排好），只排模板的文字，写出前去掉标记；编辑器的预览例外（正文带着源码行号标记排版，标记换成空的 span 之后还要再排一次）。生成器的代码改了只需重启这些线程，预处理的状态不丢。完整构建（`npm run build`）用的是同一套代码。

每个输出文件，服务记下生成的 HTML 的哈希与搜索文档：哈希与上次相同的文件不再完成、也不再写入。这份记录也保存在 `.build/preview-outputs.bin`：`serve` 再次启动时，`.build/preview/` 中与记录相符的文件留用；完成页面的代码（`scripts/site/finish.mjs`、`scripts/search/`、`scripts/shared/`、bananamark（含 TikZ 插件））改了则作废。

预处理渲染好的正文保存在 `.build/render-cache/`（`scripts/prebuild/render-cache.mjs`，约 65 MB）：键是页面的文档、渲染器得知的页面信息（分区、语言、排版设置、页面种类），以及渲染器的代码、数据与站点地址；每条还记下渲染时向全站提出的问题与得到的回答（链接的条目的地址、页面的地址、链接的种类、页面目录中的文件）。只有这些回答都与现在相同时才取用，所以不必为依赖关系另写规则。渲染了全部页面的预处理之后，删去这次没用到的条目。站点地址是键的一部分，换了端口的第一次启动不能取用。

搜索索引在页面之后、请求的间隙在后台重写（文档都取自上面的记录，约 5 s），写完后 `serve` 换上新的 `/pagefind/`，在此之前继续提供上一次的索引；新的修改到来时，尚未开始的重写合并到下一次。只有搜索文档或清单变了才重写，所以部分重建之后搜索也随之更新。

浏览器订阅时带上当前路径，服务器记录每个文件最近一次内容变化的版本号，只通知内容确实变化的页面刷新；样式、脚本与 static/ 的文件变化时所有页面都刷新。部分重建同时重新生成 `sitemap.xml`、别名跳转表与编辑器的条目名列表。

实测（2514 篇，各缓存已有内容），与完整构建相比：

| 修改 | 完整构建 | 增量更新 |
| --- | --- | --- |
| 启动 `serve` | 28.6 s | 10.5–11 s（预处理约 6.8 s，其中渲染正文约 2.4 s；生成约 4 s；搜索索引在其后约 5 s） |
| 样式（`assets/scss`） | 30.5 s | 0.4 s |
| `static/` 中的文件 | 32.6 s | 0.2 s |
| 一种页面的模板 | 31.9 s | 2.0 s |
| 所有页面共用的模板部分 | 31.9 s | 8–9 s |
| `i18n/`（不改变页面时） | 33.3 s | 9.2 s |

### 部分重建

预览服务渲染页面时用的是全站最新的数据，但只渲染要求的页面：分类页、列表页、书册目录读取其他页面的标题，链接取决于目标的地址，所以一个页面变化时，还要找出依赖它的页面一起重新渲染。正文中的链接由预处理渲染，所以链接目标变化的依赖页面也重新转换（prebuild 的 `rerender`），变化的写入生成目录。

`scripts/prebuild/affected.mjs` 比较修改前后的全站状态（prebuild 的 `pageIndex()`：每页的地址、条目名与别名、分类），决定还要重新渲染哪些页面：

- 名称（条目名或别名）指向的页面、地址或“是否别名”有变化时，链接到这些名称的页面。各页面的链接目标取自元数据与转换后的正文（`linkTargets()`），所以也包括导航框中的链接。
- 变化的页面所属的分类页（含上级分类）、所在各级目录的页面（`index.md`）、所在书册的全部页面、首页（统计数字）、编辑器页面（条目名列表）。有分类页要重新渲染时，也重新渲染分类总览 `/categories/`：为此 prebuild 把它写成页面 `categories/index.md`。
- 分类树变化时全部分类页；分类的集合变化时，正文中含有分类链接的页面（链接是否标为分类取决于分类是否存在）。
- 附件变化时它所属的页面。附件是源文件的硬链接，源文件原地修改时生成目录中的也已改变，所以变化的附件一律重新发布（复制到页面旁）。

不再输出的文件（删除、改名、变成草稿的页面，以及随之发布的附件）从快照与 `.build/preview/` 中删除。重新渲染的页面完成后（与完整构建相同：`scripts/site/finish.mjs` 与 TikZ）写入 `<output>/public/`，`serve` 与快照比较，只发布内容变化的文件；完成的页面按生成器的 HTML 缓存，未变的页面不必再处理。

结果与完整构建逐字节一致：`tests/serve.mjs` 在一系列部分重建（改名、分类、书册标题、新建与删除目录、附件、分类树、导航框、Git 提交）之后完整构建一次，比较 `.build/preview/` 中的全部文件（搜索索引、`sitemap.xml` 与旧的带指纹文件除外）。在真实内容上也逐字节比较过。

## 完整构建的耗时

完成页面（排版、搜索文档、序列化）由站点生成器在内存中进行（`scripts/site.mjs`、`scripts/site/finish.mjs`）：模板生成的页面直接交给 worker 线程，每页只解析一次。页面体积大是这一步慢的主因（KaTeX 的 HTML 与 MathML 使一篇 15 KB 的源文件生成约 400 KB 的 HTML），所以解析之前取出 KaTeX 的 HTML（页面字节的一半；排版不进入公式，搜索读取公式的 MathML），排版与生成搜索文档之后序列化，再放回。主线程替换 TikZ 图形（一个 TeX 进程、一份缓存）、写出页面，并按页面生成的顺序把索引版 HTML 交给 Pagefind，所以结果与 worker 的数目和完成顺序无关。

站点模型只在内存中保留页面的 front matter（直接从文件的字节中解码，不切取正文的字符串，否则整页都留在内存中），正文在模板需要时从磁盘读回：全站正文约 1 GB 的堆因此降到约 150 MB。2514 篇（2836 个 HTML 文件）时，站点生成（含静态文件、资源、页面与搜索索引）的用时与峰值内存：

| worker | 页面写完 | 含搜索索引 | 峰值内存 |
| --- | --- | --- | --- |
| 1 | 19.4 s | 21.7 s | 1.16 GB |
| 2 | 14.4 s | 16.6 s | 1.47 GB |
| 4（默认） | 12.7 s | 15.1 s | 1.91 GB |
| 8 | 13.0 s | 15.3 s | 2.08 GB |

四个以上没有好处：主线程（站点模型约 2.5 s、模板约 1.5 s、TikZ、交给 Pagefind 约 5.7 s）成了瓶颈。服务器只有 4 GB 内存，默认最多 4 个（CPU 核数减一），可用 `--jobs N` 改变。全站构建约 30 s（预处理约 16 s，站点生成约 14 s；TikZ 缓存已有全部的图时）。

## 常驻预览服务与在线编辑

### 常驻预览服务

`scripts/preview-service.mjs`。`serve` 以子进程方式使用它，API（`scripts/api.mjs`）在同一进程中使用它。预览一个页面需要全站的 front matter、条目名索引、分类与书册结构，它们在两次预览之间不变；本页正文的转换只要几十毫秒。所以服务是一个常驻的 Node 进程：

1. 启动时完成全站预处理，全站 front matter、条目名索引、分类与书册结构保存在内存里。
2. 请求只解析变化的页面：用内存中的索引做重名检查与规范化，转换正文（书册页面重新转换所在书册）。
3. 站点生成器（`scripts/site/`）在同一进程内渲染并完成该页后返回。请求排队依次处理。

两种请求：`serve` 的修改已经保存在 `content/` 中，结果成为新的全站状态，生成目录随之更新（供之后的完整构建）；在线预览的稿件只在全站状态的副本上计算，不改变它，也不写任何文件：生成器的站点模型由全站的页面加上稿件生成的页面构成，稿件的页面在它们的真实位置，所以地址、所属分区、面包屑、书册侧栏的当前页、条目索引都与正式构建相同。因为请求依次处理，前一份稿件改动的标题、别名或分类不会出现在下一次预览中。

站点模型每次请求重新建立（2514 篇时约 25 ms）；页面的 front matter 只解析一次，按内存中的页面对象缓存，正文只在渲染该页时才解压。生成器的模块与资源（样式与脚本的地址，`scripts/site/assets.mjs`）在完整预处理之后第一次渲染时载入，所以模板出错时是渲染失败，而不是预处理失败。

稿件中新出现的分类不生成分类页（不改变全站的分类表）。草稿、未来日期等未发布的页面没有预览输出，是否发布按 prebuild 的规则判断。

被预览的页面中的公式先用 KaTeX 检查（`packages/bananamark/src/syntax/katex-check.mjs`，选项与渲染相同，同样经过站点的 `rewriteMath`（`scripts/shared/math.mjs`，替换 `\mathbb{1}` 等）；交换图除外），浏览器内检查也一样：KaTeX 无法渲染的公式报告为“第 x 行：公式无法渲染：KaTeX 的说明”，标在该公式上。完整构建不做这项检查（会把每个公式渲染两次）；测试核对站点上的全部公式都能通过。预览接口的日志列出各步的时间：`prebuild`、`render`（生成器）与 `finish`（完成页面）。

服务启动后先预热：预览一个临时的新页面（含缓存中没有的公式），让 KaTeX、生成器（含资源的构建）与完成页面的模块都完成初始化，约 2 s。预览接口在预热完成后才开始接受请求；`serve` 在完整构建后于后台预热，每个服务进程一次。

预览接口只在内存中保留页面的 front matter（`prebuild({ frontMatterOnly: true })`）：渲染一个页面只需要其他页面的 front matter，条目之间不读取正文，书册的编号与跨页引用已由预处理写进本页。这样的生成目录不能用于完整构建，所以 `serve` 仍使用完整的正文。

没有 TikZ 新图形的预览不等待任何输入输出，在一次事件循环中完成；同时到达的请求实际上依次完成，不会排起长队。只有编译新图形的预览会让后来的请求等待（排队上限见下文）。

完成的页面最多缓存 200 个（每页约 1 MB），先淘汰最久未用的。缓存按生成器输出的 HTML：书册整组重新渲染，但修改一页正文时，其他页面的 HTML 通常不变，不必再处理。

实测（2514 篇，预览接口的设置，即 production 环境、只保留 front matter）：

| 预览 | 耗时 | 其中 |
| --- | --- | --- |
| 条目正文（“光滑流形”“拓扑空间”） | 46–65 ms | 预处理 16–26 ms，渲染 23–33 ms，完成 4–10 ms |
| 书册页面（抽象代数“引子”，整本书重新转换） | 169–184 ms | 预处理 107–121 ms（其中书册的转换约 80 ms），渲染 55–60 ms，完成 4–7 ms |

### API

`npm run api`（`scripts/api.mjs`）启动常驻服务和一个只监听本机的 HTTP 服务（默认 `127.0.0.1:8787`），由 Apache 把 `/api/` 转发过来；配置见 [服务器部署](deploy.md#apache)，已在本地用 Apache 2.4 验证。预览使用 production 环境（`--environment`）和 site.yaml 的 `baseURL`，与正式构建一致，预览页面中的样式、字体等地址（带指纹的文件名）都指向 Apache 提供的站点。生成目录为 `.build/api/content`，不与同一工作目录中的 `npm run build` 冲突。

- `GET /api/source?path=…`：页面当前的源文本与它的 blob id（`original`），书册页面另有书中其他页面的标签（`labels`，供补全）；登录用户对该页有未合并的 PR 时，取 PR 分支上的版本，`minor` 为这个 PR 是否把页面标为小修改（提交对话框的勾选框由此开始）。`pulls` 列出在线编辑器为该页开的全部未合并 PR（`{ number, url, author, title }`，不论是谁开的）；`&pull=<编号>` 取其中一个 PR 的版本（已合并或关闭时退回默认版本，并在 `pullMissing` 中给出编号），`&pull=none` 取网站上的版本。
- `POST /api/preview`，`{ path, text }`：`path` 为 `content/` 中的页面（可以是新页面），`text` 为完整源文本。返回 `{ ok, url, html, missingLinks, timings }`。
- `POST /api/check`，同样的参数：只检查，返回 `{ ok, missingLinks }`。
- `POST /api/submit`，`{ path, text, original, message, pull, minor }`：检查通过后把文本用 `npm run format` 的规则排版（`scripts/format/markdown.mjs`，只改换行与缩进，页面不变）再提交，打开或更新该用户对该页的 PR，提交说明的末尾写上这个页面是否小修改（`minor`，`Minor-edit:` 或 `Major-edit:` 加页面的路径，见开发文档的“小修改”）；给出 `pull`（PR 编号）时添加到该页的这个 PR（可以是别人的；已不再打开时不写入，返回 410，带上是否已合并 `merged`，以及不带 `pull` 提交时的基础 `current` 与该用户自己的 PR `pull`），见下；返回 `{ ok, number, url, updated, original, text }`，`text` 是提交的（排版后的）文本，编辑器随即显示它（提交期间又有输入时保留输入）。
- `GET /api/page-history?path=…`：修改该页面而尚未出现在网站上的 PR（待审阅的，以及已合并而 API 所在的提交还不包含的），供页面历史补在构建时写出的历史之前。不需要登录：所有页面共用一份待审阅 PR 的列表，每分钟至多向 GitHub 读取一次，每个来源地址（Apache 加在 `X-Forwarded-For` 最后的一项；IPv6 按 /64 网段）可以连续请求 20 次，之后每 2 秒一次。`/api/recent-changes` 与 `/api/recent-changes/diff` 同样按来源地址限频（各自计数）。
- 登录：`GET /api/auth/login?return=…`、`GET /api/auth/callback`、`POST /api/auth/logout`、`GET /api/me`。
- 错误返回 `{ ok: false, errors: [{ file, line, message }] }`：预处理与渲染错误为 422，未登录 401，跨站请求 403，过于频繁 429（带 `Retry-After`），请求体超过 300 KiB 为 413，排队超过 20 个为 503。
- `GET /api/health`：`{ ok, waiting }`。

各接口的参数与选项见 `scripts/api.mjs` 开头的说明。

**稿件能做什么。** 稿件进入常驻的预览服务，因此除了内容检查，还限制它能让生成器做的事：

- 路径：只能是 `wiki/`、`books/`、`help/` 下的页面，即自己目录中的 `index.md`（条目、栏目的页面、书与章）；条目只能是 `wiki/<名称>/index.md`，不能位于另一个条目的目录中。路径不超过 300 字符、8 层。
- front matter：只能使用作者的字段（`scripts/prebuild/front-matter-rules.mjs` 的 `authorKeys`：title、aliases、categories、navboxes、sort、lang、numbering、typography、tocDepth、search、description）；`markup`、`layout`、`url`、`outputs`、`cascade`、`draft` 等会改变页面布局与发布的字段报错。完整构建另外检查 `url`、`slug` 是站内地址。
- 标签：作者写 `<see>` 等标签（bananamark 的 HTML 式标签；站点的标签见 [页面的写法](syntax.md#站点的方言)），由 bananamark 按各标签的设置检查参数后换成节点（页面提示、`<see>`、`<person>` 是站点加上的，`scripts/shared/tags.mjs`；编辑器在浏览器中的检查也用 `scripts/shared/syntax.mjs` 中同样的设置），其他 HTML 标签报错。
- 链接与图片：只允许站内地址与 http、https（链接另有 mailto），图片地址经过转义；Markdown 中的原始 HTML 本来就不输出。预览 iframe 还设置了 sandbox，不运行脚本。
- 资源：请求体不超过 300 KiB；一次预览的 TikZ 编译总共不超过 20 s（`totalTimeout`，消息 `tikz_total_timeout`），单个图形 15 s；TeX 运行在内存文件系统中，读不到主机文件。YAML 别名有数量上限。预处理、编辑器语法与各扫描器对任何输入都是近似线性的时间：`tests/adversarial.mjs` 把 56 种病态模式各重复到 30 000 字符（单行与多行），要求每一步在 2 s 内完成。

**登录与限流。** 预览、检查和提交都需要用 GitHub 登录。登录只用来确认身份：OAuth 不请求任何权限，换得的令牌取得用户名后即丢弃。会话是签名的 cookie（`HttpOnly`、`SameSite=Lax`，30 天），服务器不保存会话。带 cookie 的 POST 如果来自其他网站（`Origin` 不同）则拒绝；JSON 请求体本身也需要跨站预检，而预检永远不会通过。预览按账号限流：可以连续 3 次（快速打开几个页面时各自立刻预览），之后每 3 s 恢复一次（`--preview-interval`）；检查的最短间隔为它的 1/3，提交为 5 倍。被拒绝时返回 429 与 `Retry-After`，并打印一行日志；每次预览也打印一行日志，含页面、总耗时与各步耗时（总耗时多出的部分是排队）。请求依次处理，一次条目预览约 50 ms。

**提交。** PR 由机器人令牌创建，用户不需要授予任何仓库权限。每个用户对每个页面使用一个分支 `edit/<用户名>/<路径的哈希>`：没有未合并的 PR 时，从目标分支建立（合并或关闭后残留的同名分支重置到目标分支），提交后开 PR；已有未合并的 PR 时，在该分支上追加 commit，PR 随之更新。commit 的作者是登录的用户（`<id>+<用户名>@users.noreply.github.com`），合并后计入用户的贡献；PR 正文注明由谁提交，并链接到编辑器中的该 PR（`/edit/?path=…&pull=<编号>`；PR 建立后才知道编号，所以随即改写一次正文）。

**编辑别人的 PR。** 打开的页面有别人用在线编辑器开的未合并 PR 时，编辑器先请用户选择编辑哪个版本：其中一个 PR，或网站上的版本（用户自己有 PR 时则是自己的 PR，因为自己对该页的提交总是进入它）；关闭对话框保留默认的版本，地址中有 `pull` 时不询问。编辑期间该 PR 被合并或关闭时，提交返回 410，编辑器保留修改，转到新的基础（网站上的版本，或用户自己的 PR）：PR 原样合并、网站版本没有别的变化时，只提示并提供“提交为新的 PR”；否则先以比较视图标出差异（PR 未合并时，其中包括该 PR 中被放弃的修改），确认后提交即开新的 PR（或添加到自己的 PR）。在别人的 PR 上提交时，commit 追加到该 PR 的分支，作者是提交的用户，机器人在 PR 中留言 `@用户 通过在线编辑器更新了此 PR`，通知 PR 的作者。只认仓库自身的 `edit/<用户名>/<路径的哈希>` 分支，fork 中同名的分支不算。任何登录用户都能向这些 PR 追加 commit，与维基的编辑方式相同；合并前仍由维护者审阅，每个 commit 的作者可查。冲突检测：编辑器打开页面时记下源文本的 blob id，提交时与目标分支（或 PR 分支）上该文件当前的 blob id 比较，不同则不写入，返回 409 与当前版本，由编辑器处理。有预处理错误的稿件不提交。

**GitHub 设置。** OAuth App、提交用的 token 与会话密钥的设置步骤见 [在线编辑的 GitHub 设置](editor-setup.md)。密钥只从环境变量读取（`BANANA_SESSION_SECRET`、`BANANA_GITHUB_CLIENT_ID`、`BANANA_GITHUB_CLIENT_SECRET`、`BANANA_GITHUB_TOKEN`），可以用 `--env-file` 从文件读入。`tests/api-github.mjs` 用一个模拟的 GitHub 测试登录、提交与冲突。

### 编辑器页面

`/edit/?path=wiki/条目/index.md`（`content/edit/index.md`，模板 `scripts/site/templates/special.mjs` 的 `editorContent`，脚本 `assets/js/editor/main.js`）。CodeMirror 6 由 esbuild 从 `node_modules` 打包（`scripts/site/assets.mjs`），是站点生成的一步，不需要另外的构建步骤。每个结构化页面的页脚有“编辑本页”链接；没有 `path` 时，页面请用户输入条目名或页面路径，新的名称即新建条目。界面文字在 `i18n/zh-cn.yaml` 的 `editor_` 各键。

- 打开页面时取 `/api/source`；已登录且对该页有未合并的 PR 时，编辑的是 PR 中的版本。该页有别人的 PR 时先请用户选择（见上“编辑别人的 PR”），选择后带上 `&pull=` 重新载入；提交成功后地址也换成该 PR 的，重新打开时继续编辑它。
- 语法高亮、补全、编辑公式（`\[` 自动配对、回车补全 `\]`）与浏览器内检查来自 bananamark-codemirror（[README](../packages/bananamark-codemirror/README.md)，英文；语法本身是 bananamark 的 `bananamark/grammar`，渲染器高亮代码块也用它）。编辑器没有用包的 `bananamark()` 一次装好，而是逐项装上（`assets/js/editor/main.js` 的 `setup()`：折叠标记要用站点的图标，补全与检查用站点的设置）。站点给它的：方言的语言（`scripts/shared/dialect.mjs`，```` ```terms ```` 按 YAML 高亮）；站点标签的规则（`scripts/shared/syntax-rules.mjs`）；补全的设置与站点自己的一种补全（`scripts/editor/completion.mjs`：环境与中文名来自 `data/theorems.yaml`，条目名与别名、语言名称（`data/language_names.yaml`），以及导言区 `categories` 中的分类）。条目名、分类、环境与语言名称由编辑器页面的模板在构建时写成一个带指纹的 JSON，第一次需要时才取；KaTeX 的命令表随 bananamark-codemirror 打包进编辑器的脚本。书册页面还补全同一书册其他页面的标签：常驻预处理为每个书册保留共同的标签表（`collectionLabels`），`GET /api/source` 随源文本返回其中不属于本页的标签，带上引用显示的样子（如“第 1 章”“定理 1.1.1”）与所在页面的标题，排在本页的标签之后。`tests/markdown-language.mjs` 用全部页面核对语法：找到的公式与构建逐一相同，百科链接与环境围栏都被识别。
- 颜色取自网站本身（`assets/scss/_highlight.scss`，类名 `bm-hl-*`，站点的代码块共用）：百科链接显示的文字为链接蓝（`[[目标|文字]]` 中不显示的目标为灰色）；环境名与代码块的语言为定义的橙色，环境标题 `[标题]` 的文字为灰色（与行内代码相同），方括号与行内标记一样为浅灰；块结构（列表标记、`>`、`:::`、代码围栏、分隔线、导言区的 `---`）为浅橙色，标题的 `#` 为浅灰；引用与标签为定理的紫色，其中的 `@` 与花括号为浅紫色；TeX 命令与 YAML 的键为定理的青绿色（文字用的青绿色深一些），YAML 的数字为定义的橙色；公式中的数字与其余的字母为正文色；行间公式的分隔符与代码围栏一样为浅橙色，行内公式的 `$`、`\(`、`\)` 为浅青绿色；行内代码为灰色文字。CodeMirror 的界面（行号、当前行、选区、括号匹配、折叠、搜索面板、提示框、补全列表）按网站的样式重写；搜索面板等 CodeMirror 自己的文字由 `EditorState.phrases` 译成中文（`i18n` 的 `editor_cm_*`）。
- 站点的代码块与编辑器一致：bananamark 渲染代码块时用同一套语法与类名高亮（`<pre class="bm-code-block" data-highlight="语言">`），帮助页面中的 Markdown 示例与编辑器中的样子相同；其他常见语言（`sh`、`python` 等）由 `bananamark/languages` 高亮（`scripts/prebuild/render.mjs`），没有语法的语言照原文写出。
- 预览只在请求时进行：工具栏的“预览”按钮（悬停提示快捷键）、Ctrl+S / ⌘S，以及打开页面时一次；点击“提交”时，若当前文本还没有预览成功，先预览，成功后才打开对话框，有错误则不打开（错误显示在预览上）；文本与上次预览相同时什么也不做。输入时不自动预览：那会让预览不停地闪动，服务器也一直忙碌；浏览器内检查仍在输入时标出错误，遮罩只在预览时显示。两次请求至少相隔 3 s，与服务器的限流一致，收到 429 时按 `Retry-After` 安静地重试。预览在路上时（无论由“预览”还是等待预览的“提交”发起），“预览”按钮左边显示一个转动的圆环；请求失败（如网络问题）时状态处显示“预览失败，点击此处重试”。预处理或渲染的错误不显示在状态处，而是以等宽字体显示在预览上方的白色半透明遮罩中，下一次成功预览后消失。错误与缺失条目也标在对应的行上（行号旁的图标与文字下的波浪线）。修改了标记范围内的文字（替换、删除，或在其中输入），这个标记立即消失：它可能已经不成立；浏览器内检查在 0.3 s 后重新标出仍然存在的错误，服务器发现的问题则等下一次预览。在标记之前或之后输入不影响它，服务器的标记随编辑移动。预览中隐藏站点的导航栏、本页目录、页脚（含其分隔线）与书册页面的上一页/下一页链接，并收窄标题上方的间距。源码不自动换行：缩进保持清楚，也不鼓励过长的行。Tab 先接受补全中选中的一项；没有补全时，没有选中文字则在光标处插入空格，到下一个 2 的倍数列，选中了文字则缩进其所在的行。Shift+Tab 减少所在行的缩进。缩进以 2 个空格为单位（与源文件的缩进一致）。回车换行并缩进到当前行文字开始处：列表项目从首行起即缩进到项目的文字（`-` 后两格，`1.` 后三格，`(a)` 后四格），引用保留 `>`，与 `npm run format` 的续行缩进相同（共用 `packages/bananamark/src/syntax/scan.mjs` 的 `continuation`）；不自动添加列表标记，因为本站的列表项目大多有多行，列表也多是松散的（项目之间空行）。光标两侧的空格去掉，只有空格的行留空；在一行的标记之中按回车只换行。导言区、代码块与行间公式中仍是 CodeMirror 自己的回车。退格删去列表标记或缩进（CodeMirror 的 `deleteMarkupBackward`）。除了标题，导言区（两行 `---` 之间）与环境（`::: 名称` 到对应的 `:::` 之前，嵌套的环境分别计算，代码块中的 `:::` 不算）也可以折叠。
- 浏览器内检查发现错误时，不再请求服务器预览，错误直接显示在预览上的遮罩中；遮罩中的“第 x 行”可以点击，跳到代码中的那一行。工具栏的“提交”总可以点；对话框中的“提交”要等当前文本成功预览后才可用，在此之前说明原因（等待预览或需要修正错误），预览完成后随即可用。
- “条目尚未创建”页面（`scripts/site/templates/special.mjs` 的 `missingContent`，脚本 `static/js/missing.js`）有“创建条目”链接，打开 `/edit/?title=<标题>`。标题取链接中写下的目标（含 TeX，如 `怪 $\mathbb{R}^4$`）：预处理给缺失链接加上 `source` 参数（与显示名称相同时省略），缺失页面把它传给编辑器。编辑器按已有条目的约定由标题得到目录名（`scripts/shared/names.mjs` 的 `directoryName`）：公式写成纯文字并去掉其中的空格，空心体等字母改为普通字母，Windows 不允许的 `/\:*?"<>|` 改为全角，去掉末尾的点；例如 `怪 R^4`，网址为 `/怪_R^4/`。新条目的 `title` 保留原标题。编辑器首页只接受条目名（不能含 `/`），同样作为标题。在线编辑只能新建条目（`wiki/<名称>/index.md`）：编辑器打开其他不存在的页面时只显示提示，API 拒绝提交其他新页面（403）；已有的其他页面照常编辑。
- 导言区的必要项目（`scripts/prebuild/front-matter-rules.mjs`）：页面必须有导言区，其中 `title` 为非空文字（完整构建在没有 title 时取目录名）。只在编辑器中检查：浏览器内检查，以及 API 的预览、检查与提交。新条目的模板为 `title`、`categories: []`、`navboxes: []`。
- 问题只标在代码中（行号旁的标志：错误为叉，警告为黄色三角形），没有单独的列表：条目不存在很常见，列表会被它们占满。错误与缺失条目带有列号（预处理的错误对象带 `column`，条目链接报告时也带列号），只标出该处的链接或词，不划整行；列号不出现在说明文字中。服务器报告的问题按当时预览的文本定位，再随之后的每次编辑移动（`ChangeSet.mapPos`），所以在下一次预览之前也标在原来的词上。
- 浏览器内检查：停止输入 0.3 s 后，在浏览器中运行预处理自己的解析（`assets/js/editor/check.js`），不经过服务器即标出错误，修正后随即消失。只检查一个页面自己就能决定的部分：front matter 的语法、标题与别名、正文。书册页面引用书中其他页面的标签，按打开页面时 `GET /api/source` 返回的这些标签（`labels`，也用于补全）检查：标签不存在、与其他页面的标签重复都在浏览器中标出；书册共同的编号取决于书的设置与页面在书中的位置，不在浏览器中检查（每个目标都视为有编号），条目链接是否存在取决于全站，这些仍由预览报告。以前书册页面只由服务器检查，其标记只在修改标记内的文字时消失，于是在 `\[`、空行、`\]` 的空行中输入后，“公式没有结束”仍标在 `\[` 上，直到下一次预览。与预处理一样，遇到第一个错误即停止。实现：esbuild 直接打包 `scripts/prebuild/` 中的模块（`scripts/site/assets.mjs`，`../scripts/` 指向仓库的 `scripts/`）；`node:fs` 换成垫片，读取构建时嵌入的语言表与 `data/theorems.yaml`。打包后约 740 KB（gzip 约 220 KB，主要是 KaTeX 与 parse5），在编辑器显示之后才加载；加载失败时，下一次检查重新加载。
- 第一次预览载入 iframe；之后只要样式表不变，就在已显示的文档中原地替换正文与内联样式，不重新载入，因此不会有样式未加载时的闪烁（`serve` 的样式表不缓存，每次载入都要重新取得），也更快，滚动位置保持不变。样式表变了才重新载入：载入在两个交替的 iframe 中隐藏的那个里进行，完成后才显示，并保持滚动位置。
- 源码行号标记（`packages/bananamark/src/syntax/source-lines.mjs`，只用于编辑器的预览，完整构建不受影响）：预处理在被预览页面每一行源码的行首（缩进、列表与引用标记、项目的 `{@标签}` 之后）插入行号标记，由私用区字符写成，以标点 U+2E3D 结尾（Markdown 判断强调时，行首与标点等价）；改变语法的行不加：标题、`:::`、表格、分隔线、公式块、图片、链接定义，以及行首落在代码块（任意缩进）、行内代码或公式中的行。参考文献块（`bibliography` 代码块）的各行因此没有标记，预处理改在它生成的每个条目开头标上该条目的键所在的行（`structure.mjs`，页面带有标记时），长的参考文献也能对齐。完成页面时（`scripts/site/finish.mjs`），排版之前把标记换成空的 `<span data-source-line="N">`，属性与 `<head>` 中的标记删去。错误与缺失链接的列号扣除标记的长度，仍按原始源码计算。去掉这些 span 之后，预览与完整构建的 `<body>` 逐字节一致（抽查 307 页，唯一的例外是 TikZ 图中按全站计数的 clip 编号，单页预览原本就从 1 开始）；`<head>` 中按长度截取的摘要（`og:description`）因标记占用长度而变短。
- 滚动源码时，预览滚到对应位置；只跟随用户自己的滚动（滚轮、触控、拖动滚动条、翻页与方向键），不跟随跳转、输入时光标带动的滚动和 CodeMirror 测量行高时的调整；预览有错误或失败时不跟随；滚动预览时源码同样跟随（预览的框架不运行脚本，Chrome 也不在其中触发 scroll 事件，所以每一帧读取它的位置，变化不是源码引起的就滚动源码）。对应关系以行号标记为锚点（标记的行号属于当时预览的文本，随之后的编辑换算到当前文本），其间线性插值；没有标记时以标题为锚点。窄屏切换到“预览”时，预览显示光标所在行的位置（光标所在行在源码区中的高度保持），切换回“代码”时源码显示预览顶部对应的位置。点击错误的行号时，源码把该处滚到中间，预览保持不动。iframe 的 `sandbox` 只有 `allow-same-origin`（和打开新标签页的 `allow-popups`），不允许脚本：稿件中的任何内容都不会执行，站点自己的脚本（导航栏偏移、本地时间等）在预览中也不运行。同源使样式与字体照常加载，编辑器可以读取预览的滚动位置；链接在新标签页打开；指向本页的链接（脚注、引用、标题锚点，`#id` 或本页地址加 `#id`）改为在预览中滚动，使目标位于顶端（只滚动预览本身；站点为导航栏留出的滚动边距在预览中不需要）：预览的文档地址是编辑器的地址，`#id` 会在框架中载入编辑器页面。曾考虑不同源的沙盒（opaque origin），但它加载站点的样式、字体与模块脚本都要 CORS，而且在有些浏览器环境中（如 Claude 桌面应用的内置浏览器）对本机地址的请求全部被拦截。Chrome 不给禁止脚本的文档派发滚动事件，所以滚动位置在下一次预览载入时直接读取。
- 行号旁标出每行相对服务器版本（打开页面时取得的版本；提交成功或得知更新的版本后改为该版本）的修改：新增的行为绿色竖条，修改的行为蓝色竖条，删除之处为红色三角（在删除处之前一行的下端；删去开头的行时在第一行上端）。逐行比较，与 git 相同：每个不同的行化为一个字符，再比较两个字符串；一段行被更多的行替换时，前面与原来同样多的行算修改，其余算新增。标记所在的一栏比标记宽，便于点击，指针移到标记上时标记略微变大（以 `transform` 缩放，动画平滑；改变尺寸会逐像素跳动），竖条居中，向两侧变宽。行号之后只留很小的空白，问题标记一栏只有标记宽（CodeMirror 默认为 1.4em）。点击标记，在标记所在的行之下（删去开头的行时在第一行之上）以页面历史的差异页面的样式显示这处修改（只读的 CodeMirror 与 `unifiedMergeView`，样式共用 `_recent-changes.scss` 的 `%diff-codemirror`）：原来的行为红色，现在的行为绿色，其中改动的文字加深；只有新增或只有删除时只显示新增或删去的行（另一边是空的文本，即一个空行，不显示）。旁边是“还原”按钮：还原把这处修改的各行换回原来的行，是一次编辑，可以撤销；再次点击标记、Esc、关闭按钮或任何编辑都关闭它。紧挨着的修改与新增是同一处修改，一起还原。
- 修改随时保存在本机（localStorage），并记下草稿基于的版本（blob id）。再次打开时：页面未变则自动恢复草稿，提示可以关闭；页面在保存草稿之后被修改过（别人的修改已合并，或自己的 PR 有了新提交），则不自动加载，提示并提供“加载草稿”与“放弃草稿”，加载后在合并视图中标出草稿与当前版本的差异。
- 提交时可以填写修改说明；成功后显示 PR 链接。返回 409 时，以合并视图显示你的版本与最新版本的差异，下一次提交以最新版本为基础。
- `tests/editor-page.mjs` 在 jsdom 中用构建出的页面与脚本测试这些流程。

本地开发：

```sh
npm run api -- --dev-user 你的名字 --base-url http://127.0.0.1:1414/ --environment development
npm run serve -- --port 1414 --api http://127.0.0.1:8787
```

`serve --api` 把 `/api/` 转发给 API，与正式环境中 Apache 的作用相同；API 使用 development 环境，预览中的样式地址才与 `serve` 一致。`--dev-user <名字>` 跳过 GitHub 直接登录（只能在监听本机地址时使用）。

实测（2514 篇）：启动约 6.5 s（预处理 4.5 s，预热约 2 s，其中构建资源约 1.5 s）；预览的耗时见上文。

内存（macOS，`--expose-gc` 下每步之后回收）：活的数据约 170 MB，其中模块、代码与 KaTeX、CodeMirror、拼音的数据约 105 MB，全站的记录、元数据、源文本与 Git 历史约 40 MB，生成器的模块与资源约 15 MB，压缩的生成页面约 5 MB。为此：

- 压缩的生成页面复制到大小正好的缓冲区（`exactCopy`），而不是 64 KB 缓冲区池（`Buffer.poolSize`）中的小片：每片会留住整块。
- 书册转换后的文档在完整预处理之后丢掉（只有 front matter 时用不到；稿件会重新转换整组书册）。
- 生成的页面带着预处理的元数据对象（`metadata`），生成器直接使用，不再解析一份 front matter。
- esbuild 构建资源之后停止它的服务进程（`esbuild.stop()`）。
- 稿件的预览不进完成页面的缓存（稿件不会重复）。

进程的常驻内存比活的数据大得多：V8 等到堆长到约 300 MB 才做完整的回收，预处理时的高峰也不立刻还给系统。不加限制时预览 200 次后约 1.0–1.1 GB；以 `node --max-old-space-size=512` 运行（`npm run api` 与服务器上的 systemd 单元都这样做）时稳定在约 0.58 GB，预览的耗时不变；限制为 384 MB 时约 0.5 GB，但大书册的稿件重新转换整组时余地太小。

`tests/api.mjs` 检查：条目正文、新别名、新页面与书册页面的预览与完整构建逐字节一致；前一份稿件的别名不影响下一次预览；20 个并发请求（含同一页面两次、含空格与大写的路径）各自得到正确结果；预览之后生成目录与未预览时完全相同（稿件不写入任何文件）；错误行号、未发布页面、重名与请求限制。

### 服务器部署

Apache 提供静态文件（站点与编辑器页面），并用 mod_proxy 把 `/api/` 转发到 `127.0.0.1` 上的 API，编辑器与接口同源，无需 CORS，登录 cookie 直接可用。API 以普通用户运行（systemd 用户单元），只监听本机。API 启动时读取全站，站点更新后需要重启。目录布局、定时部署与 Apache 配置见 [服务器部署](deploy.md)。
