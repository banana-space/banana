# 预览与检查

条目达到数千篇后，完整构建需要数十秒到数分钟。本文说明单页预览、检查、`serve` 增量更新、常驻预览服务与在线编辑的设计。

## 命令

```sh
npm run preview -- content/wiki/条目甲 content/wiki/条目乙/index.md
npm run check -- content/wiki/条目甲
```

`preview` 输出在 `.build/page-preview/public/`，使用相对地址，可直接以 `file://` 打开；命令列出每页的输出路径、缺失条目链接（含行号）和 Hugo 警告，再次运行会替换上次的输出。`check` 只运行预处理，不调用 Hugo：收集全部错误而不是在第一个错误处停止，并报告缺失条目链接；指定页面时只报告与它们有关的错误（含与它们冲突的重名错误），不指定页面则检查全站；有错误时退出码为 1。两个命令都支持 `--json` 输出结构化结果，以及 `--buildDrafts` 等发布参数（只接受 `--flag` 或 `--flag=value` 形式）。`npm run bench` 用合成条目测量完整构建与单页预览的耗时。

`npm run serve` 的预览输出在 `.build/preview/`，使用开发样式和 source map。同一份源码同时只能运行一个 `serve`，第二个会提示后退出：两者会构建到同一目录。

## 依赖关系

一个页面的输出依赖：

- 本页的正文与 front matter；
- 全站 front matter：条目名与别名决定链接颜色和地址，分类、书册目录、列表页使用标题与排序键；
- 共享定义：模板、样式、`data/`、`i18n/`、提示与导航定义、构建脚本、Hugo 配置；
- 同一书册的其他页面：编号与跨页引用；
- Git 提交日期。

其他页面不读取百科条目的正文（跨页引用只存在于书册内），所以**只改正文时，只有本页需要重新渲染**；书册页面的正文影响同组页面的编号与引用，只需重新渲染整组书册。这是单页路径的基础。

## 单页路径

`npm run preview`（`scripts/preview.mjs`）一次性渲染指定页面：

1. prebuild 照常读取并规范化全站 front matter（重名检查、条目索引、分类、书册），但只转换目标页面的正文；其他页面写成只有 front matter 的空正文。书册整组转换。生成内容写入独立目录，不影响 `.build/content`。
2. Hugo 用 `--renderSegments` 只渲染目标页面。全站页面仍然加载，`GetPage`、条目索引和分类都正确。
3. postbuild 只处理输出的页面，不建搜索索引。

结果与完整构建的同一页面逐字节一致（除了地址前缀）。每次运行都要重新预处理全站并让 Hugo 加载全部页面，2257 篇时约 4 s；`serve` 改用下面的常驻预览服务。

## serve 的增量更新

`serve` 记录 `content/` 的文件列表、各页面的 front matter 与 `data/` 的文件列表（完整构建前，以及每次更新成功后）。之后的修改按下列规则处理，结果都合并进内存快照与 `.build/preview/`：

- 只有已有页面的正文变化（front matter 不变）：交给常驻预览服务单页更新（`render`）。书册页面（包括 `content/help/` 中的指南）重新渲染所在书册的全部页面，含自动目录页。
- 已有页面的 front matter 变化，或在已有目录中新建页面：只重新转换这些页面（`renderPages`），再重新渲染依赖它们的页面（见下文“部分重建”）。页面用到分类表中没有的分类时改用下一条（只有完整预处理才生成分类页）。
- 删除、改名、新建目录、附件、`collection.yaml`、提示与导航定义、`data/categories.yaml`、Git 提交：在预览服务中完整预处理（`refreshSite`，约 3.6 s），只把变化的生成文件写给常驻的 Hugo，同样重新渲染依赖它们的页面。
- 模板、样式、脚本、`i18n/`、其他 `data/` 文件与配置：完整构建。
- 出现又消失的路径（编辑器临时文件，包括 `data/` 中的）：忽略。
- 上次完整构建失败后，一律完整构建，直到成功。源文件的错误（预处理失败）不改变任何状态，修正后连同这次的修改一起处理；部分重建的其他失败（如 Hugo 报错）改为完整构建。

完整构建的预处理也在预览服务中完成，所以服务始终持有最近一次成功的全站状态；`scripts/` 有修改时，下次完整构建前重启服务以载入新代码。服务在完整构建成功后才启动 Hugo，避免与完整构建的 Hugo 争用 CPU。单页结果与完整构建逐字节一致，`tests/serve.mjs` 检查了这一点。

完整构建的 postbuild 处理完全部页面后即通知 `serve`（IPC 消息），`serve` 随即发布新快照、通知浏览器刷新；postbuild 接着写入搜索索引（约 2 s），写完后 `serve` 换上新的 `/pagefind/`，在此之前继续提供上一次的索引。索引写入失败时保留旧索引，下一次修改完整构建；新的完整构建开始时，尚未写完的索引直接放弃。

浏览器订阅时带上当前路径，服务器记录每个文件最近一次内容变化的版本号，只通知内容确实变化的页面刷新；完整构建后内容未变的页面也不刷新。单页更新与部分重建不更新搜索索引与 `sitemap.xml`，下次完整构建时补上；Hugo 不再输出的带指纹的旧文件（如更名后的 `js/editor-names.<hash>.json`）也留到那时才删除。

### 部分重建

Hugo 的增量重建只重新渲染生成文件变化了的页面，不知道页面之间的依赖：条目名索引（`layouts/partials/wiki/index.html`）由 `partialCached` 缓存，分类页、列表页、书册目录读取其他页面的标题，都不会自动更新。实测把“拓扑空间”改名后，Hugo 只重新渲染了它本身，链接到它的 244 个页面仍是旧链接。把这些页面的生成文件原样重写一遍，Hugo 就会用新的全站数据重新渲染它们。

`scripts/prebuild/affected.mjs` 比较修改前后的全站状态（prebuild 的 `pageIndex()`：每页的地址、条目名与别名、分类），决定还要重新渲染哪些页面：

- 名称（条目名或别名）指向的页面、地址或“是否别名”有变化时，链接到这些名称的页面。各页面的链接目标取自元数据与转换后的正文（`linkTargets()`），所以也包括提示与导航框中的链接。
- 变化的页面所属的分类页（含上级分类）、所在各级分节的 `_index.md`、所在书册的全部页面、首页（统计数字）、编辑器页面（条目名列表）。有分类页要重新渲染时，也重新渲染分类总览 `/categories/`：为此 prebuild 把它写成页面 `categories/_index.md`（标题与 Hugo 的默认标题相同；正式构建的输出不变，开发构建的 `<html>` 多一个 `data-source` 属性）。
- 分类树变化时全部分类页；分类的集合变化时，正文中含有分类链接的页面（链接是否标为分类取决于分类是否存在）。
- 附件变化时它所属的页面。附件是源文件的硬链接，源文件原地修改时生成目录中的也已改变，所以变化的附件一律重新发布，Hugo 才会收到事件。

不再输出的文件（删除、改名、变成草稿的页面，以及随之发布的附件）从快照与 `.build/preview/` 中删除。新输出与变化的输出从 Hugo 的输出目录中找：重建开始后写过的文件，与上次记录的哈希比较，只有内容变化的 HTML 才做 postbuild（服务内、依次处理，与单页路径相同）。服务在 Hugo 启动并预热后记录全部输出的哈希。

Hugo 一次收到不超过约 50 个文件事件时只重建这些页面（约 0.35 s 后察觉，重建 0.1–0.25 s）；超过时停顿约 4 s 再重建整个网站（2257 篇时 5–9 s）。先写临时文件再 rename 的原子写入约产生三个事件，所以重写依赖页面时在原文件上写回同样的字节（不截断，任何时刻读到的都是完整文件，只产生一个事件）。写入分批进行，每批不超过约 40 个事件并等 Hugo 重建完成：先写变化的文件（每批 13 个），最后一批带上第一批依赖页面，其余依赖页面每批 40 个；变化的文件跨了几批时，前几批的页面最后再重写一次，因为后写的修改可能影响它们。某一批若引起整站重建，此后不必再重写依赖页面。Hugo 的日志在整站重建时不列出源文件，以 `Rebuilt in` 结束，视为覆盖了开始前已写完的文件。

结果与完整构建逐字节一致：`tests/serve.mjs` 在一系列部分重建（改名、分类、书册标题、新建与删除目录、附件、分类树、提示与导航框、Git 提交）之后完整构建一次，比较 `.build/preview/` 中的全部文件（搜索索引、`sitemap.xml` 与旧的带指纹文件除外）。在真实内容上（2257 篇）也逐字节比较过。实测（从保存到浏览器可见）：

| 修改 | 耗时 | 重新渲染 |
| --- | --- | --- |
| 加一个别名、改分类 | 0.75–1.1 s | 2–6 页 + 7–10 个依赖页面 |
| 把“紧空间”设为草稿 | 3.2 s | 148 页（127 个依赖页面） |
| 把“拓扑空间”改名（244 个页面链接到它） | 5.0–5.3 s | 247 页（250 个依赖页面），其中 Hugo 约 3.5 s、postbuild 约 1.2 s |
| 改导航框（35 个页面使用） | 5.8–6.3 s | 38 页；预处理 3.7 s |
| 新建条目目录、改名目录、附件、分类树、Git 提交 | 4–6 s | 主要是预处理 3.6 s |

此前这些修改都要完整构建（约 12 s；未启用 postbuild 缓存时约 19 s，最初约 60 s）。

## 实测

`npm run bench` 生成 3000 个合成条目（以现有条目为样本）测量。以下为 Apple Silicon 笔记本上的结果：

| 操作 | 耗时 |
| --- | --- |
| 完整构建（冷 / 热缓存） | 117 s / 47 s |
| `npm run preview` 单页 | 1.8 s |
| `npm run check` 单页 / 全站 | 0.8 s / 5.7 s |
| `serve` 修改正文到浏览器可见 | 0.3–0.7 s（见下文“常驻预览服务”） |
| `serve` 修改标题（完整构建） | 49 s |

postbuild 曾是完整构建中最长的一段（单线程约 27–35 s，其中 parse5 解析与序列化约 15 s、排版约 4 s、TikZ 约 4 s、搜索约 8 s）。页面体积大是主因：KaTeX 的 HTML 与 MathML 使一篇 15 KB 的源文件生成约 400 KB 的 HTML。现在页面分给 worker 线程处理（`scripts/postbuild/worker.mjs`），主线程只编译 TikZ（一个 TeX 进程、一份缓存）并按文件顺序把各页的索引版 HTML 交给 Pagefind，所以结果与 worker 的数目和完成顺序无关。2257 篇（2571 个 HTML 文件）时处理完页面的用时与峰值内存：

| worker | 页面 | 峰值内存 |
| --- | --- | --- |
| 1 | 22 s | 1.0 GB |
| 2 | 13 s | 0.9 GB |
| 4（默认） | 8.5 s | 1.4 GB |
| 8 | 7 s | 2.3 GB |

服务器只有 4 GB 内存，默认最多 4 个（CPU 核数减一），可用 `--jobs N` 改变。写入搜索索引另需约 2 s。

`serve` 的完整构建还复用上一次的结果（`--cache .build/postbuild-cache`，`scripts/postbuild/cache.mjs`）：每个页面保存 Hugo 输出的哈希、处理后的 HTML、索引版 HTML，以及页面用到的 TikZ 字体和图形缓存键。Hugo 输出、搜索清单中该页的条目与代码（`scripts/` 全部文件、`static/js/search-query.js`、`package-lock.json`）都不变时，直接写回保存的 HTML、复制字体，并把图形计为已使用（否则 `--prune-cache` 会删掉它们的缓存）。修改 front matter 时，Hugo 重新输出的大多是内容相同的页面，所以几乎都不必再处理。改模板、样式或脚本时所有页面都要重新处理，与不用缓存一样。缓存约 480 MB，不存在的页面在每次构建后删除。正式构建（`npm run build`）不使用缓存。

`serve` 修改 front matter 后的完整构建（2257 篇）因此从约 60 s 降到约 12 s：预处理约 3.8 s、Hugo 约 5.5 s、postbuild 约 1.5 s（2571 页中 2569 页取自缓存；无缓存时约 8.6 s），读入快照约 0.3 s；搜索索引在此后约 4 s 写好（Pagefind 仍要接收全部页面）。剩下的时间主要在预处理与 Hugo；front matter 与其他内容的修改现在多数不必完整构建，见上文“部分重建”。

## 常驻预览服务与在线编辑

### 单页预览的时间花在哪

2257 篇时，`npm run preview` 预览任何页面都要 3.7–4.1 s，与页面长短无关：

| 步骤 | 耗时 | 性质 |
| --- | --- | --- |
| prebuild：读取并规范化全站 front matter | 0.85 s | 全站 |
| prebuild：书册整组转换（预览百科条目时也做） | 0.7 s | 全站 |
| prebuild：为全部页面生成 YAML 与读音元数据 | 0.6 s | 全站 |
| prebuild：Git 日期、写出 | 0.2–0.5 s | 全站 |
| Hugo `--renderSegments` | 0.7–1.0 s | 主要是加载全部页面 |
| postbuild | 0.17 s | 其中约 0.1 s 是进程启动 |

本页正文的转换只要几十毫秒。全站部分在两次预览之间不变，应当留在内存里，而不是搬到浏览器。

常驻的 `hugo server --renderToMemory` 修改一个条目正文后，Hugo 报告的重建时间为 80–165 ms，从写入文件到取得新 HTML 为 0.38–0.59 s（多出的主要是文件监听延迟）；冷启动 5.8 s，内存约 290 MB。

### 常驻预览服务

`scripts/preview-service.mjs`。`serve` 以子进程方式使用它，编辑接口（`scripts/editor-api.mjs`）在同一进程中使用它。一个常驻 Node 进程，管理一个 `hugo server` 子进程：

1. 启动时完成全站预处理，全站 front matter、条目名索引、分类与书册结构保存在内存里。
2. 请求只解析变化的页面：用内存中的索引做重名检查与规范化，转换正文（书册页面重新转换所在书册），写入 Hugo 监听的生成目录。
3. 等 Hugo 重建完成后取得 HTML，在同一进程内对该页做 postbuild 后返回。请求排队依次处理。

两种请求：`serve` 的修改已经保存在 `content/` 中，结果成为新的全站状态；在线预览的稿件只在全站状态的副本上计算，不改变它。稿件生成的页面写在它们的**真实位置**，直到下一次请求才换回全站的版本：换回的内容与下一份稿件一起写入，Hugo 只重建一次，所以还原不增加耗时；空闲 30 s 后也会单独还原。因为请求依次处理，每次预览看到的都是全站加上这一份稿件：前一份稿件改动的标题、别名或分类，在下一次预览之前已经换回。

曾考虑把稿件写到单独的沙盒页面（如 `content/_preview/slot-1/`），不碰原页面。没有采用：沙盒页面与原页面同名，会在条目索引中冲突（同名时以后写入的为准，指向该条目的链接可能指到沙盒）；模板中的地址、所属分区、面包屑、书册侧栏的当前页都依赖页面位置；页面目录中的附件也不在沙盒里。这些都会使预览与正式构建不同。

稿件中新出现的分类不生成分类页（不改变全站的分类表）。草稿、未来日期等未发布的页面没有预览输出：Hugo 的输出目录会保留页面变成草稿之前的版本，所以是否发布按 prebuild 的规则判断，而不是看 Hugo 是否返回 404。应当发布的页面 Hugo 却返回 404 时，把该文件原样重写一次，等 Hugo 再次重建后重取：Hugo 不渲染与其目录同时出现在内容目录顶层的新页面（新的一节，如 `content/a/b/index.md`），直到页面再次改变。

被预览的页面中的公式在交给 Hugo 之前先用 KaTeX 检查（`scripts/prebuild/katex-check.mjs`，选项与 `layouts/partials/math.html` 相同，同样替换 `\mathbb`；交换图除外），浏览器内检查也一样：KaTeX 无法渲染的公式报告为“第 x 行：公式无法渲染：KaTeX 的说明”，标在该公式上，而 Hugo 的错误既不指出位置也不指出是哪个公式。完整构建不做这项检查（会把每个公式渲染两次）；测试核对站点上的全部公式都能通过。其他 Hugo 错误报告其最内层的原因（`hugoMessage`），不再只是“hugo failed”。预览接口的日志把 Hugo 的时间分成两部分：`hugo notice` 是写入之后到 Hugo 发现变化（日志中的 `Change detected`）的时间，`hugo build` 是 Hugo 自己报告的重建时间（`Total in`）。实测改动“光滑流形”时，重建约 0.1 s，而发现变化要 0.3–0.4 s：Hugo 的文件监听把事件攒成一批再处理，间隔不能设置。偶尔几秒的预览，若 notice 与 build 都不慢，多半是机器负载（本机完整重建网站、内存不足时 Hugo 被换出到交换区）。Hugo 是否已完成包含这次写入的重建，根据它的日志判断：每次重建列出变化的源文件（`Source changed /wiki/…/index.md`，路径改为小写、空格改为 `-`），以 `Total in … ms` 结束，其间的 `ERROR` 行即重建错误。一次写入可能分在几次重建中，所以等到写入的每个文件都出现过；若日志漏列了某个文件，在 Hugo 空闲 1.5 s 后继续并给出警告。两种情况日志不列出写入的文件：Hugo 只监听启动时已有的目录，新建或删除的目录记为其中的 `_index.md`，视为覆盖目录下所有文件；修改配置时 Hugo 重建整站（`Change of config file detected` … `Rebuilt in … ms`），视为覆盖在它开始之前已写完的文件。设置环境变量 `BANANA_PREVIEW_DEBUG=1` 可以看到 Hugo 的全部日志。

Hugo 启动后先预热：预览一个临时的新页面（含缓存中没有的公式）再删除它，让文件监听、增量重建、KaTeX 与 postbuild 模块都完成初始化，约 1 s。预览接口在预热完成后才开始接受请求；`serve` 在 Hugo 启动后于后台预热，每个 Hugo 进程一次。曾有一次启动后的第一次预览用了 4.6 s（全在 Hugo），未能复现；预热之后，启动后的第一次预览为 0.27–0.39 s。

Hugo 渲染到 `<output>/hugo/`，而不是内存：2257 篇时内存少约 1 GB，增量重建一样快（约 100 ms）。

预览接口的 Hugo 只读取页面的 front matter（`prebuild({ frontMatterOnly: true })`），只有被预览的页面写入正文；书册稿件的同组页面只写入新的 front matter。页面正文占 Hugo 绝大部分内存，而渲染一个页面只需要其他页面的 front matter：条目之间不读取正文，书册的编号与跨页引用已由预处理写进本页。2257 篇时 Hugo 的内存因此从约 1.9 GB 降到约 0.47 GB（所有正文都留空时 370 MB，只清空条目正文时仍有 1.6 GB：书册正文占了大半）。这样的生成目录不能用于完整构建，所以 `serve` 仍使用完整的正文。用真实内容抽查 42 个页面（含 TikZ、提示、导航框与书册），预览与正式构建逐字节一致。

postbuild 缓存最多保留 200 个页面（每页约 1 MB），先淘汰最久未用的。

postbuild 结果按 Hugo 输出的原始 HTML 缓存：书册整组重新渲染，但修改一页正文时，其他页面的 HTML 通常不变，不必再处理。

`serve` 中实测（2257 篇，从保存到浏览器可见）：

| 修改 | 耗时 | 其中 |
| --- | --- | --- |
| 条目正文 | 0.3–0.7 s | 预处理约 10 ms，Hugo 0.27–0.6 s，postbuild 约 10 ms |
| 讲义页面正文（整组 44 页） | 约 0.8 s | 预处理约 130 ms，Hugo 约 0.6 s，postbuild 约 50 ms |
| 同上，服务启动后第一次 | 约 2.2 s | postbuild 缓存为空，44 页都要处理 |

剩下的时间大部分是 Hugo 文件监听的合批延迟。

### 编辑接口

`npm run editor-api`（`scripts/editor-api.mjs`）启动常驻服务和一个只监听本机的 HTTP 服务（默认 `127.0.0.1:8787`），由 Apache 把 `/api/` 转发过来；配置见 [服务器部署](deploy.md#apache)，已在本地用 Apache 2.4 验证。Hugo 使用 production 环境和 hugo.toml 的 `baseURL`，与正式构建一致，预览页面中的样式、字体等地址都指向 Apache 提供的站点。生成目录为 `.build/api/content`，不与同一工作目录中的 `npm run build` 冲突。

- `GET /api/source?path=…`：页面当前的源文本与它的 blob id（`original`），书册页面另有书中其他页面的标签（`labels`，供补全）；登录用户对该页有未合并的 PR 时，取 PR 分支上的版本。
- `POST /api/preview`，`{ path, text }`：`path` 为 `content/` 中的页面（可以是新页面），`text` 为完整源文本。返回 `{ ok, url, html, missingLinks, timings }`。
- `POST /api/check`，同样的参数：只检查，返回 `{ ok, missingLinks }`。
- `POST /api/submit`，`{ path, text, original, message }`：检查通过后把文本用 `npm run format` 的规则排版（`scripts/format/markdown.mjs`，只改换行与缩进，页面不变）再提交，打开或更新该用户对该页的 PR，见下；返回 `{ ok, number, url, updated, original, text }`，`text` 是提交的（排版后的）文本，编辑器随即显示它（提交期间又有输入时保留输入）。
- 登录：`GET /api/auth/login?return=…`、`GET /api/auth/callback`、`POST /api/auth/logout`、`GET /api/me`。
- 错误返回 `{ ok: false, errors: [{ file, line, message }] }`：预处理与 Hugo 错误为 422（Hugo 错误另带 `log`），未登录 401，跨站请求 403，过于频繁 429（带 `Retry-After`），请求体超过 300 KiB 为 413，排队超过 20 个为 503。
- `GET /api/health`：`{ ok, waiting }`。

各接口的参数与选项见 `scripts/editor-api.mjs` 开头的说明。

**稿件能做什么。** 稿件进入常驻的 Hugo，因此除了内容检查，还限制它能让 Hugo 做的事：

- 路径：只能是 `wiki/`、`books/`、`help/` 下的页面，即自己目录中的 `index.md`（不能是栏目本身的 `wiki/index.md`，那会让整个栏目变成一个页面）或书册、章节的 `_index.md`；新页面不能与已有的 `index.md`/`_index.md` 同目录，也不能位于另一个页面的目录中。路径不超过 300 字符、8 层。
- front matter：只能使用作者的字段（`scripts/prebuild/front-matter-rules.mjs` 的 `authorKeys`：title、aliases、categories、navboxes、notices、sort、lang、numbering、typography、tocDepth、search、description）；`markup`、`layout`、`url`、`outputs`、`cascade`、`draft` 等会改变 Hugo 行为的字段报错。完整构建另外检查 `url`、`slug` 是站内地址。
- shortcode：页面中不能出现（见 [写作语法](syntax.md) 的“标签与 shortcode”）；作者写 `<see>` 等标签，由预处理检查参数后换成 shortcode。Hugo 内置的 shortcode 会读取远程内容或嵌入外部页面，模板内部的会输出不成对的 HTML；Hugo 在代码块中和 `RenderString` 的字符串中也执行 shortcode，所以检查整个源文件，生成的页面（含 front matter 的所有字符串）交给 Hugo 之前再查一遍。其他 HTML 标签报错。
- 链接与图片：只允许站内地址与 http、https（链接另有 mailto），图片地址经过转义；Markdown 中的原始 HTML 本来就不输出。预览 iframe 还设置了 sandbox，不运行脚本。
- 资源：请求体不超过 300 KiB；一次预览的 TikZ 编译总共不超过 20 s（`build_tikz_budget`），单个图形 15 s；TeX 运行在内存文件系统中，读不到主机文件。YAML 别名有数量上限。预处理、编辑器语法与各扫描器对任何输入都是近似线性的时间：`tests/adversarial.mjs` 把 56 种病态模式各重复到 30 000 字符（单行与多行），要求每一步在 2 s 内完成。

**登录与限流。** 预览、检查和提交都需要用 GitHub 登录。登录只用来确认身份：OAuth 不请求任何权限，换得的令牌取得用户名后即丢弃。会话是签名的 cookie（`HttpOnly`、`SameSite=Lax`，30 天），服务器不保存会话。带 cookie 的 POST 如果来自其他网站（`Origin` 不同）则拒绝；JSON 请求体本身也需要跨站预检，而预检永远不会通过。预览按账号限流：可以连续 3 次（快速打开几个页面时各自立刻预览），之后每 3 s 恢复一次（`--preview-interval`）；检查的最短间隔为它的 1/3，提交为 5 倍。被拒绝时返回 429 与 `Retry-After`，并打印一行日志；每次预览也打印一行日志，含页面、总耗时与各步耗时（总耗时多出的部分是排队）。请求依次处理，每次约 0.5 s，所以整个服务每秒约能处理两次预览。

**提交。** PR 由机器人令牌创建，用户不需要授予任何仓库权限。每个用户对每个页面使用一个分支 `edit/<用户名>/<路径的哈希>`：没有未合并的 PR 时，从目标分支建立（合并或关闭后残留的同名分支重置到目标分支），提交后开 PR；已有未合并的 PR 时，在该分支上追加 commit，PR 随之更新。commit 的作者是登录的用户（`<id>+<用户名>@users.noreply.github.com`），合并后计入用户的贡献；PR 正文注明由谁提交。冲突检测：编辑器打开页面时记下源文本的 blob id，提交时与目标分支（或 PR 分支）上该文件当前的 blob id 比较，不同则不写入，返回 409 与当前版本，由编辑器处理。有预处理错误的稿件不提交。

**GitHub 设置。** OAuth App、提交用的 token 与会话密钥的设置步骤见 [在线编辑的 GitHub 设置](editor-setup.md)。密钥只从环境变量读取（`BANANA_SESSION_SECRET`、`BANANA_GITHUB_CLIENT_ID`、`BANANA_GITHUB_CLIENT_SECRET`、`BANANA_GITHUB_TOKEN`），可以用 `--env-file` 从文件读入。`tests/editor-github.mjs` 用一个模拟的 GitHub 测试登录、提交与冲突。

### 编辑器页面

`/edit/?path=wiki/条目/index.md`（`content/edit/index.md`，布局 `layouts/_default/editor.html`，脚本 `assets/js/editor/main.js`）。CodeMirror 6 由 Hugo 的 `js.Build` 从 `node_modules` 打包，完整构建、`serve` 与编辑接口用的是同一个 Hugo，不需要另外的构建步骤。每个结构化页面的页脚有“编辑本页”链接；没有 `path` 时，页面请用户输入条目名或页面路径，新的名称即新建条目。界面文字在 `i18n/zh-cn.yaml` 的 `editor_` 各键。

- 打开页面时取 `/api/source`；已登录且对该页有未合并的 PR 时，编辑的是 PR 中的版本。
- 语法高亮（`scripts/shared/markdown-language.mjs`，编辑器与之后构建时的代码块共用）：CommonMark 加上 GFM 的表格、任务列表、删除线与自动链接（不含 `~下标~` 等扩展），以及本站的语法：导言区（YAML）；公式 `$…$`、`$$…$$`、`\(…\)`、`\[…\]`，其中按 TeX 高亮（一个小的流式分词器：命令与 `^`、`_`、`&`，`\begin{…}`/`\end{…}` 中的环境名，括号，数字，注释，`\text{…}` 等命令中的文字（其中的 `$…$` 又是公式，如 `$a\text{$b$}c$`）；`latex`、`tex` 代码块从公式外开始，标出 `\[ \]` 等分隔符）；百科链接、`@标签` 与 `{@标签}`、环境围栏 `::: 名称 [标题] {@标签}`、Hugo 短代码、脚注；`math`、`tikz` 围栏按 TeX，`terms`、`bibliography`、`yaml` 按 YAML，`markdown` 按本语法。公式在哪里结束、引用标签在哪里结束，用的是构建本身的扫描（`scripts/shared/scan.mjs`，从 `markup.mjs` 移出，不依赖 KaTeX）。公式的各行可能看起来像 Markdown（单独一行 `=` 会成为标题下划线，`+ x` 会开始列表），所以独占几行的行间公式整体作为一个块；段落中未闭合的公式在判断段落结束的各项检查之前就把后续行收进段落（这一检查放在解析器列表的最前面）。表格的单元格不在百科链接和公式内部分割，与构建一致（`[[甲|乙]]`、`$|x|$` 在表格中不必转义）。`tests/markdown-language.mjs` 用全部页面核对：语法找到的公式与构建逐一相同（183288 个），百科链接（31623 个）与环境围栏（26050 个）都被识别。
- 颜色取自网站本身（`assets/scss/_highlight.scss`，类名 `hl-*`，由 `tagHighlighter` 给出，供站点的代码块共用）：百科链接显示的文字为链接蓝（`[[目标|文字]]` 中不显示的目标为灰色）；环境标题 `[标题]` 为灰色；YAML 的数字为定义的橙色，与字符串区分（YAML 语法把两者都叫 Literal，形如数字的再交给一个小语法标出；为此导言区由本语法自己识别，而不用 lang-yaml 的 `yamlFrontmatter`）；环境名与代码块的语言为定义的橙色，块结构（列表标记、`>`、`:::`、代码围栏、分隔线、导言区的 `---`）为浅橙色，标题的 `#` 与行内标记一样为浅灰；引用与标签为定理的紫色（比原来的紫色略淡，定理框中的紫色同样），其中的 `@` 与花括号为浅紫色；TeX 命令与 YAML 的键为定理的青绿色（文字用的青绿色深一些）；公式中的数字与其余的字母为正文色；行间公式的分隔符 `\[`、`\]`、`$$` 与代码围栏一样为浅橙色，行内公式的 `$`、`\(`、`\)` 为浅青绿色；行内的标记符号（强调的 `*`、行内代码的反引号等）为浅灰，行内代码为灰色文字。代码块的信息串（`math {@eq:x}`）由一个小的流式语法分出语言与标签。CodeMirror 的界面（行号、当前行、选区、括号匹配、折叠、搜索面板、提示框、补全列表）按网站的样式重写；搜索面板等 CodeMirror 自己的文字由 `EditorState.phrases` 译成中文（`i18n` 的 `editor_cm_*`）。
- 补全（`scripts/editor/completion.mjs`）：行首的 `:::` 与环境名的开头补全环境（插入开始与结束围栏，光标在其间；环境名与中文名来自 `data/theorems.yaml` 与 i18n；单独的 `:::` 是环境的结束，不弹出补全），名称之后可以接着写标题与标签的简写（`:::th 标题 @标签` 成为 `::: theorem [标题] {@标签}`），只在行末输入时弹出（在标题或标签中修改时不弹出）；页面的围栏已经配对时（修改已有环境的开始行），确认只改写这一行，不再插入正文行与结束围栏，行首的 ```` ``` ```` 补全 `math`、`tikz`、`terms`、`bibliography` 代码块，`[[` 之后输入了 `$` 以外的字符才补全条目标题（照原样写出公式的 TeX）与别名并补上 `]]`，`@`、`{@` 补全本页声明的标签（标题末尾、环境围栏、列表项目开头、`math` 围栏），导言区 `categories` 中输入了字符才补全分类（删回到 `[[` 或空的分类时候选消失）。公式中（本语法的公式、`math`/`tikz`/`latex`/`tex` 代码块，以及正在输入、尚未闭合的公式）`\` 加字母补全 KaTeX 命令（带上所需的花括号，光标在第一个之中），`\begin{` 之后补全环境（插入 `\begin`、缩进两格的空行与 `\end`；公式中的 `\begin` 与 `\end` 已经配对时，即修改已有环境的名称，确认同时改写对应的 `\end`）；命令与环境都只在名称的末尾补全；命令与环境的列表 `data/katex.json` 由 `scripts/editor/katex-commands.mjs` 从 KaTeX 自身的定义生成（KaTeX 能渲染的才保留，定义宏、链接与 HTML 的命令以及本站公式中不能用的 `align` 等环境除外，另加不属于 KaTeX、由 TeX 编译的 `tikzcd` 与 `tikzpicture`，升级 KaTeX 后重新运行；测试核对文件是否最新）。在 `\` 之后输入 `[` 或 `(`（不是 `\\` 之后）直接成对：`\[|\]`，两者之间为空时退格一起删去；`\\` 是换行，其后的字母不补全命令。一行中只有 `\[`（可带成对的 `\]`）时按回车，成为 `\[`、空行与 `\]`，三行的缩进相同（与 `npm run format` 的排版一致）。`<` 加字母补全标签（插入开始与结束标签，光标在接着要写的地方；在已有的标签中只改名称），`</` 补全尚未结束的标签的结束标签，`<lang ` 之后与 `<person … lang="` 中补全语言代码（`data/language_names.yaml`，随条目名一起写入 JSON），`<align ` 之后补全 `right`、`center`（这两处的取值与参数名一样显示为青绿色，用参数的图标），`<person`、`<spoiler` 中补全尚未写出的参数名；插入 `<lang `、`<align `、`<person ` 后列表随即打开。输入法组字时不补全，组字结束后在链接目标与分类中开始补全。每种候选有自己的图标（环境、代码块、条目、别名、标签、分类、HTML 式标签、参数、取值），颜色与语法高亮一致。条目名、分类与环境由编辑器页面的模板在构建时写成一个带指纹的 JSON（约 87 KB，gzip 约 19 KB），第一次需要时才取。书册页面还补全同一书册其他页面的标签（书册页面可以引用它们）：常驻预处理为每个书册保留共同的标签表（`collectionLabels`），`GET /api/source` 随源文本返回其中不属于本页的标签，带上引用显示的样子（按书册的 `referenceFormat`，如“第 1 章”“定理 1.1.1”）与所在页面的标题，排在本页的标签之后。
- 站点的代码块与编辑器一致：语言为 `markdown`/`md`、`yaml`、`latex`/`tex` 的代码块，由 Hugo 的代码块钩子（`layouts/partials/code-block.html`）输出为不高亮的 `<pre class="code-block" data-highlight="语言">`，postbuild（`scripts/postbuild/code-blocks.mjs`，只在有这种代码块的页面上加载）用编辑器的同一套语法与类名高亮，所以帮助页面中的 Markdown 示例与编辑器中的样子相同，示例中嵌套的 ```` ```math ````、```` ```terms ```` 等也一样。其他语言（`sh`、`text` 等）仍由 Hugo 的 Chroma 在构建时高亮。两种代码块外观相同（浅灰底、较小的字号）。编辑器的预览也经过 postbuild，所以预览帮助页面时同样高亮。
- 预览只在请求时进行：工具栏的“预览”按钮（悬停提示快捷键）、Ctrl+S / ⌘S，以及打开页面时一次；点击“提交”时，若当前文本还没有预览成功，先预览，成功后才打开对话框，有错误则不打开（错误显示在预览上）；文本与上次预览相同时什么也不做。输入时自动预览曾经让预览不停地闪动，服务器也一直忙碌，所以不再自动预览；浏览器内检查仍在输入时标出错误，遮罩只在预览时显示。两次请求至少相隔 3 s，与服务器的限流一致，收到 429 时按 `Retry-After` 安静地重试。预览在路上时（无论由“预览”还是等待预览的“提交”发起），“预览”按钮左边显示一个转动的圆环；请求失败（如网络问题）时状态处显示“预览失败，点击此处重试”。预处理或 Hugo 的错误不显示在状态处，而是以等宽字体显示在预览上方的白色半透明遮罩中，下一次成功预览后消失。错误与缺失条目也标在对应的行上（行号旁的图标与文字下的波浪线）。修改了标记范围内的文字（替换、删除，或在其中输入），这个标记立即消失：它可能已经不成立；浏览器内检查在 0.3 s 后重新标出仍然存在的错误，服务器发现的问题则等下一次预览。在标记之前或之后输入不影响它，服务器的标记随编辑移动。预览中隐藏站点的导航栏、本页目录、页脚（含其分隔线）与书册页面的上一页/下一页链接，并收窄标题上方的间距。源码不自动换行：缩进保持清楚，也不鼓励过长的行。Tab 与 Shift+Tab 以 2 个空格为单位缩进或减少缩进（与源文件的缩进一致）。除了标题，导言区（两行 `---` 之间）与环境（`::: 名称` 到对应的 `:::` 之前，嵌套的环境分别计算，代码块中的 `:::` 不算）也可以折叠。
- 浏览器内检查发现错误时，不再请求服务器预览，错误直接显示在预览上的遮罩中；遮罩中的“第 x 行”可以点击，跳到代码中的那一行。工具栏的“提交”总可以点；对话框中的“提交”要等当前文本成功预览后才可用，在此之前说明原因（等待预览或需要修正错误），预览完成后随即可用。
- “条目尚未创建”页面（`layouts/_default/missing.html`）有“创建条目”链接，打开 `/edit/?title=<标题>`。标题取链接中写下的目标（含 TeX，如 `怪 $\mathbb{R}^4$`）：预处理给缺失链接加上 `source` 参数（与显示名称相同时省略），缺失页面把它传给编辑器。编辑器按已有条目的约定由标题得到目录名（`scripts/prebuild/names.mjs` 的 `directoryName`）：公式写成纯文字并去掉其中的空格，空心体等字母改为普通字母，Windows 不允许的 `/\:*?"<>|` 改为全角，去掉末尾的点；例如 `怪 R^4`，网址为 `/怪_R^4/`。新条目的 `title` 保留原标题。编辑器首页只接受条目名（不能含 `/`），同样作为标题。在线编辑只能新建条目（`wiki/<名称>/index.md`）：编辑器打开其他不存在的页面时只显示提示，编辑接口拒绝提交其他新页面（403）；已有的其他页面照常编辑。
- 导言区的必要项目（`scripts/prebuild/front-matter-rules.mjs`）：页面必须有导言区，其中 `title` 为非空文字（完整构建在没有 title 时取目录名）。只在编辑器中检查：浏览器内检查，以及编辑接口的预览、检查与提交。新条目的模板为 `title`、`categories: []`、`navboxes: []`。
- 问题只标在代码中（行号旁的标志：错误为叉，警告为黄色三角形），没有单独的列表：条目不存在很常见，列表会被它们占满。错误与缺失条目带有列号（预处理的错误对象带 `column`，条目链接报告时也带列号），只标出该处的链接或词，不划整行；列号不出现在说明文字中。服务器报告的问题按当时预览的文本定位，再随之后的每次编辑移动（`ChangeSet.mapPos`），所以在下一次预览之前也标在原来的词上。
- 浏览器内检查：停止输入 0.3 s 后，在浏览器中运行预处理自己的解析（`assets/js/editor/check.js`），不经过服务器即标出错误，修正后随即消失。只检查一个页面自己就能决定的部分：front matter 的语法、标题与别名、正文。书册页面引用书中其他页面的标签，按打开页面时 `GET /api/source` 返回的这些标签（`labels`，也用于补全）检查：标签不存在、与其他页面的标签重复都在浏览器中标出；书册共同的编号取决于书的设置与页面在书中的位置，不在浏览器中检查（每个目标都视为有编号），条目链接是否存在取决于全站，这些仍由预览报告。以前书册页面只由服务器检查，其标记只在修改标记内的文字时消失，于是在 `\[`、空行、`\]` 的空行中输入后，“公式没有结束”仍标在 `\[` 上，直到下一次预览。与预处理一样，遇到第一个错误即停止。实现：`hugo.toml` 把 `scripts/` 挂载为 `assets/js/scripts/`，由 `js.Build` 直接打包 `scripts/prebuild/` 中的模块；`node:fs` 换成垫片，读取构建时嵌入的语言表与 `data/theorems.yaml`，`Buffer` 也用一个小垫片代替。打包后约 740 KB（gzip 约 220 KB，主要是 KaTeX 与 parse5），在编辑器显示之后才加载；加载失败时，下一次检查重新加载。
- 第一次预览载入 iframe；之后只要样式表不变，就在已显示的文档中原地替换正文与内联样式，不重新载入，因此不会有样式未加载时的闪烁（`serve` 的样式表不缓存，每次载入都要重新取得），也更快，滚动位置保持不变。样式表变了才重新载入：载入在两个交替的 iframe 中隐藏的那个里进行，完成后才显示，并保持滚动位置。
- 源码行号标记（`scripts/prebuild/source-lines.mjs`，只用于编辑器的预览，完整构建不受影响）：预处理在被预览页面每一行源码的行首（缩进、列表与引用标记、项目的 `{@标签}` 之后）插入行号标记，由私用区字符写成，以标点 U+2E3D 结尾（Markdown 判断强调时，行首与标点等价）；改变语法的行不加：标题、`:::`、表格、分隔线、公式块、图片、Hugo 短代码、链接定义，以及行首落在代码块（任意缩进）、行内代码或公式中的行。postbuild 在排版之前把标记换成空的 `<span data-source-line="N">`，属性与 `<head>` 中的标记删去。错误与缺失链接的列号扣除标记的长度，仍按原始源码计算。去掉这些 span 之后，预览与完整构建的 `<body>` 逐字节一致（抽查 307 页，唯一的例外是 TikZ 图中按全站计数的 clip 编号，单页预览原本就从 1 开始）；`<head>` 中 Hugo 按长度截取的摘要（`og:description`）因标记占用长度而变短。
- 滚动源码时，预览滚到对应位置；只跟随用户自己的滚动（滚轮、触控、拖动滚动条、翻页与方向键），不跟随跳转、输入时光标带动的滚动和 CodeMirror 测量行高时的调整；预览有错误或失败时不跟随；滚动预览时源码同样跟随（预览的框架不运行脚本，Chrome 也不在其中触发 scroll 事件，所以每一帧读取它的位置，变化不是源码引起的就滚动源码）。对应关系以行号标记为锚点（标记的行号属于当时预览的文本，随之后的编辑换算到当前文本），其间线性插值；没有标记时以标题为锚点。窄屏切换到“预览”时，预览显示光标所在行的位置（光标所在行在源码区中的高度保持），切换回“代码”时源码显示预览顶部对应的位置。点击错误的行号时，源码把该处滚到中间，预览保持不动。iframe 的 `sandbox` 只有 `allow-same-origin`（和打开新标签页的 `allow-popups`），不允许脚本：稿件中的任何内容都不会执行，站点自己的脚本（导航栏偏移、本地时间等）在预览中也不运行。同源使样式与字体照常加载，编辑器可以读取预览的滚动位置；链接在新标签页打开；指向本页的链接（脚注、引用、标题锚点，`#id` 或本页地址加 `#id`）改为在预览中滚动，使目标位于顶端（只滚动预览本身；站点为导航栏留出的滚动边距在预览中不需要）：预览的文档地址是编辑器的地址，`#id` 会在框架中载入编辑器页面。曾考虑不同源的沙盒（opaque origin），但它加载站点的样式、字体与模块脚本都要 CORS，而且在有些浏览器环境中（如 Claude 桌面应用的内置浏览器）对本机地址的请求全部被拦截。Chrome 不给禁止脚本的文档派发滚动事件，所以滚动位置在下一次预览载入时直接读取。
- 修改随时保存在本机（localStorage），并记下草稿基于的版本（blob id）。再次打开时：页面未变则自动恢复草稿，提示可以关闭；页面在保存草稿之后被修改过（别人的修改已合并，或自己的 PR 有了新提交），则不自动加载，提示并提供“加载草稿”与“放弃草稿”，加载后在合并视图中标出草稿与当前版本的差异。
- 提交时可以填写修改说明；成功后显示 PR 链接。返回 409 时，以合并视图显示你的版本与最新版本的差异，下一次提交以最新版本为基础。
- `tests/editor-page.mjs` 在 jsdom 中用构建出的页面与脚本测试这些流程。

本地开发：

```sh
npm run editor-api -- --dev-user 你的名字 --base-url http://127.0.0.1:1414/ --environment development
npm run serve -- --port 1414 --api http://127.0.0.1:8787
```

`serve --api` 把 `/api/` 转发给编辑接口，与正式环境中 Apache 的作用相同；编辑接口使用 development 环境，预览中的样式地址才与 `serve` 一致。`--dev-user <名字>` 跳过 GitHub 直接登录（只能在监听本机地址时使用）。

实测（2257 篇）：启动约 7 s（预处理 2.8 s，Hugo 3.0 s，预热约 1 s）；单独预览一篇条目 0.22–0.65 s，讲义页面约 0.5 s；同时发出 20 个不同页面的预览，20 个结果都正确，共 10 s。内存（macOS 上的常驻内存，数字有波动）：Node 约 400–500 MB，Hugo 约 470 MB。

内存仍不够时还可以：给 Hugo 设置 `GOMEMLIMIT` 让它更积极地回收（代价是更多 CPU 时间）；Node 一侧，全站源文本与规范化后的元数据可以只保留预览需要的部分。

`tests/editor-api.mjs` 检查：条目正文、新别名、新页面与书册页面的预览与完整构建逐字节一致；前一份稿件的别名不影响下一次预览；20 个并发请求（含同一页面两次、含空格与大写的路径）各自得到正确结果；空闲还原后生成目录与未预览时完全相同；错误行号、未发布页面、重名与请求限制。

### 服务器部署

Apache 提供静态文件（站点与编辑器页面），并用 mod_proxy 把 `/api/` 转发到 `127.0.0.1` 上的编辑接口，编辑器与接口同源，无需 CORS，登录 cookie 直接可用。编辑接口以普通用户运行（systemd 用户单元），只监听本机；Hugo 子进程也只绑定 127.0.0.1。编辑接口启动时读取全站，站点更新后需要重启。目录布局、定时部署与 Apache 配置见 [服务器部署](deploy.md)。
